Connect the two servers

Use root SSH access. SSH keys and verified host keys must already work from this computer to the source, and from the source to the destination.

root@hostname or root@SSH-alias on this computer.

The SSH alias must resolve on the source. The destination must have matching Linux and Docker versions, with no Dokploy installation or workloads.

An address assigned to its network interface for Swarm. Behind NAT, use its local private IPv4; public DNS can use a different public IP.

Reconnect finds the latest job on the source and restores its destination settings. Jobs continue on the source if this window closes.

Plan a maintenance window

The move stops every Docker workload on the current server for the final copy. The old server stays stopped, including after reboot, while the destination starts.

Scheduled copy and recovery

Copy ahead of maintenance

Copy most data while the source stays available. When ready for downtime, run the final switch below.

Finish a prepared move

Stop the source, copy and verify final changes, then start the destination. After a failed final copy, resolve the reported issue and run this action again.

Resume the old server

Recovery before destination activation only. This restarts old workloads and makes the prepared copy stale. The engine refuses unless it can prove the destination has never started and is stopped.

Finish before retiring the source

  1. In Dokploy: Web Server → Server → Update IP. Review references to the old IP.
  2. Smoke test existing logins/MFA, database records, uploads/downloads, and every application's health on the destination.
  3. Update DNS A/AAAA records and provider firewalls. Verify HTTPS, OAuth, email, bots, and storage connectivity.
  4. Keep the old server stopped and retain your backup. New workers may already have changed data, even before DNS changes.

What transfers

Dokploy settings, local databases, Docker volumes and images, uploads, container state, certificates, environment values, and discovered application bind mounts.

  • External database, S3, registry, and remote-server connections keep their settings; external data stays at those services.
  • DNS, cloud firewalls, host packages, OS cron jobs, and other data outside the copied locations require separate setup.
